# 售后管理字段与迁移计划（Plan）

## 一、Summary

基于现有 `crm_return_order` / `crm_return_order_item`（沿用为售后主细表）进行兼容增强：

1. 在 `new_version/supabase_tables.md` 中补全售后管理字段说明（已有字段不重复创建，新增字段明确约束）。
2. 在 `new_version/migrations` 新增迁移 SQL，对数据库实际表结构补齐缺失字段并完成 `id` 到 `int` 自增主键改造（仅售后主细表）。
3. 采用“兼容并存”策略：保留既有 `return_*` 字段，同时新增 `after_sale_*` 字段。

---

## 二、Current State Analysis

### 1) 文档现状（new_version/supabase_tables.md）

- 已存在表：
  - `crm_return_order`（退货订单表）
  - `crm_return_order_item`（退货订单明细表）
- 当前问题：
  - 主表/细表 `id` 仍为 `text primary key`，与“int 无符号自增唯一主键”不一致。
  - 主表缺少本次要求的若干售后字段（如售后数量、售后类型、售后状态、售后单号兼容字段等）。
  - 细表虽已有部分售后字段，但缺少“售后单ID（int FK）”语义下的新关联方式与部分命名兼容字段。

### 2) 数据库现状（supabase/rebuild/init.sql）

- `crm_return_order` 与 `crm_return_order_item` 在基线建表中同样为 `id text primary key`。
- 细表中已存在以下售后相关字段：
  - `expected_after_sale_method`
  - `after_sale_reason`
  - `after_sale_material_image`
  - `issue_description`
  - `return_tracking_no`
  - `final_handling_method`
  - `return_qty`
- 主表尚未具备完整售后管理核心字段（类型、状态、数量等结构化字段不足）。

### 3) 已确认决策（来自需求澄清）

- 表名：沿用 `crm_return_order` / `crm_return_order_item`。
- 字段策略：兼容并存（保留 `return_no`/`reason`，新增 `after_sale_no`/`after_sale_reason`/`after_sale_type` 等）。
- 改造范围：仅售后主细表（不扩散到其他订单表）。
- 默认值：`after_sale_type` 非空默认 `1`，`after_sale_status` 非空默认 `0`。

## 三、Proposed Changes

### A. 更新文档：`new_version/supabase_tables.md`

#### A1. 主表 `crm_return_order`

按“已有不重复、缺失补齐”原则调整字段定义：

- 主键相关：
  - `id` 调整为 `int`，约束描述为 `not null unsigned auto_increment primary key`。
- 售后主业务新增字段（若不存在则新增）：
  - `after_sale_no text`（售后单号，兼容并存）
  - `after_sale_qty numeric(18,4) default 0`（售后数量）
  - `after_sale_type int not null default 1`（1退货 2换货 3维修）
  - `after_sale_reason text`（售后原因，兼容并存）
  - `after_sale_status int not null default 0`（0待跟进 1处理中 2已完成 3已取消 4已驳回）
- 继续保留并标记兼容字段：
  - `return_no`、`reason`、`status` 等，描述中注明“兼容保留”。

#### A2. 细表 `crm_return_order_item`

- 主键相关：
  - `id` 调整为 `int`，约束描述为 `not null unsigned auto_increment primary key`。
- 关联字段：
  - 将 `return_order_id` 在文档中定义为 `integer not null references crm_return_order(id) on delete cascade`（与主表 int 主键一致）。
  - 增加 `after_sale_order_id integer`（售后单ID，按需求术语补齐；实际落库时与主外键关系保持一致）。
- 售后字段补齐（已有则保留，不重复）：
  - `after_sale_no text`（售后单号）
  - `material_qty numeric(18,4) default 0`（物料数量；与原 `quantity` 并存时注明兼容）
  - `return_no text`（已存在，保留）
  - 其余现有字段（`expected_after_sale_method`、`after_sale_reason`、`after_sale_material_image`、`issue_description`、`return_tracking_no`、`final_handling_method`、`return_qty`）维持。

> 注：文档最终会以“售后语义优先 + 兼容旧字段”的描述方式整理，避免重复与冲突。

### B. 新增迁移：`new_version/migrations/20260428_04_upgrade_after_sale_schema.sql`

#### B1. 主表 `crm_return_order` 改造

1. 若 `id` 非 `int4`，执行“安全替换”流程：
   - 新增 `id_new integer` + sequence + default nextval；
   - 回填历史数据；
   - 设置 `not null`、唯一索引；
   - 重建主键并将 `id_new` 重命名为 `id`；
   - 添加 `check (id > 0)` 作为 unsigned 语义约束。
2. 新增缺失字段（`add column if not exists`）：
   - `after_sale_no text`
   - `after_sale_qty numeric(18,4) not null default 0`
   - `after_sale_type integer not null default 1`
   - `after_sale_reason text`
   - `after_sale_status integer not null default 0`
3. 添加枚举值域检查约束（幂等）：
   - `after_sale_type in (1,2,3)`
   - `after_sale_status in (0,1,2,3,4)`

#### B2. 细表 `crm_return_order_item` 改造

1. 若 `id` 非 `int4`，执行与主表一致的安全替换为 `int` 自增主键流程。
2. 处理外键改造（幂等）：
   - 新增 `return_order_id_new integer`；
   - 通过旧 `return_order_id` 与主表旧/新 ID 映射回填；
   - 切换外键到 `crm_return_order(id)`（int）；
   - 旧字段改名为 `return_order_id_legacy`，新字段改名为 `return_order_id`。
3. 新增缺失字段（`add column if not exists`）：
   - `after_sale_order_id integer`（可同步回填为 `return_order_id`，便于语义统一）
   - `after_sale_no text`
   - `material_qty numeric(18,4) not null default 0`
4. 添加 unsigned 语义约束：
   - `check (id > 0)`。

#### B3. 兼容与幂等性

- 全部新增字段使用 `add column if not exists`。
- 约束和索引创建前先判存在，避免重复执行失败。
- 遵循现有迁移风格：`begin; ... commit;`，并使用 `do $$ ... $$;` 包裹条件逻辑。

## 四、Assumptions & Decisions

1. “无符合”按“无符号”处理，采用 `check (id > 0)` 表达 unsigned 语义（PostgreSQL 无原生 unsigned int）。
2. 沿用 `crm_return_order` / `crm_return_order_item` 作为售后主细表，不新增新表名。
3. 兼容并存原则下：
   - 不删除 `return_no`、`reason`、`quantity` 等旧字段；
   - 新增售后语义字段用于后续业务收敛。
4. 本次只改 `new_version/supabase_tables.md` 与 `new_version/migrations` 新迁移文件，不改历史迁移文件内容。

## 五、Verification Steps

1. 文档检查：
   - `supabase_tables.md` 中 `crm_return_order` / `crm_return_order_item` 字段完整覆盖需求；
   - 不重复创建已有字段，兼容字段标注清晰。
2. SQL 结构检查：
   - 新迁移文件可重复执行（幂等）；
   - 主细表 `id` 最终为 `integer` 主键、自增、`check (id > 0)`；
   - 细表外键指向主表 `id(integer)`。
3. 字段完整性检查：
   - 主表存在：`after_sale_no`、`after_sale_qty`、`after_sale_type`、`after_sale_reason`、`after_sale_status`；
   - 细表存在：`after_sale_order_id`、`after_sale_no`、`material_qty` 及既有售后扩展字段。
4. 语义检查：
   - `after_sale_type` 仅允许 1/2/3；
   - `after_sale_status` 仅允许 0/1/2/3/4；
   - 默认值符合确认结果（type=1，status=0）。
