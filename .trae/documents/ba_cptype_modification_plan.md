# ba_cptype 表结构修改计划

## 1. 需求分析

根据用户需求，需要对 `ba_cptype`（产品类别本体）表进行以下修改：

1. **id 字段修改**：将其改为 int 类型、无符号、自动递增、唯一主键
2. **新增状态字段**：添加 `status` 字段，存储值为 1（启用）/ 0（不启用），默认值为 1
3. **parent_id 字段修改**：将其改为 int 类型
4. **同步更新文档**：修改 `new_version/supabase_tables.md` 文件
5. **生成迁移 SQL**：在 `new_version/migrations` 目录下生成修改 SQL 文件

## 2. 方案解决的问题

1. **性能优化**：将 `id` 和 `parent_id` 从 `text` 改为 `int` 类型，减少存储空间并提高查询性能
2. **数据一致性**：通过自动递增的整数 ID，确保数据唯一性和一致性
3. **状态管理**：新增 `status` 字段，实现产品类别的启用/禁用管理，提高系统灵活性
4. **结构统一**：`parent_id` 与 `id` 类型保持一致，避免类型不匹配问题
5. **文档同步**：确保数据库结构文档与实际结构保持一致
6. **迁移支持**：生成标准 SQL 迁移文件，便于在不同环境中部署

## 4. 技术考虑

1. **数据类型变更**：将 `id` 和 `parent_id` 从 `text` 改为 `int` 可能需要数据迁移，特别是如果表中已有数据
2. **外键关系**：其他表（如 `crm_product_series`、`ba_cpinfo`）可能引用了 `ba_cptype(id)`，需要确保这些外键关系在类型变更后仍然有效
3. **自动递增**：在 PostgreSQL 中，需要使用 `SERIAL` 或 `GENERATED AS IDENTITY` 来实现自动递增
4. **无符号整数**：PostgreSQL 本身不直接支持无符号整数，但可以通过约束来实现类似效果

## 5. 风险评估

### 已识别风险

1. **数据迁移风险**：如果表中已有数据，类型变更可能导致数据丢失或转换错误
2. **外键约束风险**：修改 `id` 类型可能导致其他表的外键约束失效
3. **应用代码风险**：应用代码可能依赖于 `id` 为字符串类型的假设，需要检查并更新相关代码

### 其他潜在风险

1. **兼容性风险**：如果系统中有其他组件依赖于当前的表结构，可能会出现兼容性问题
2. **测试风险**：修改后需要进行充分的测试，确保所有功能正常运行
3. **部署风险**：在生产环境中部署时，需要确保迁移过程平滑，避免服务中断
4. **数据丢失风险**：如果迁移过程中出现错误，可能会导致数据丢失

## 6. 风险缓解措施

1. **备份数据**：在进行任何修改前，对数据库进行完整备份
2. **测试环境验证**：在测试环境中先进行修改和测试，确保无问题后再部署到生产环境
