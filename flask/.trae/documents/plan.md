# 群成员同步优化方案评估报告

## 整体评分：9.5 / 10 分 (极简高效，直击痛点)

根据对 `schema.sql`、`20260421090000_crm_wx_projection.sql` 以及 `crm_wx_projection_service.py` 中的代码分析，当前采用的是**“基于 Version 的惰性全量同步 + 消息触点增量补偿”**的混合缓存方案。

该方案非常精准地解决了大群消息导致频繁全量 Upsert 的 I/O 瓶颈，同时保证了数据的完整性。

---

## 方案原理解析

### 1. 基于 Version 的惰性全量同步 (Lazy Full Sync)
- **机制**：在 `crm_wx_conversation` 表中引入了 `last_member_sync_version` 和 `last_member_synced_at` 字段。
- **触发**：当投影一条群消息时，系统会对比原始通讯录表 (`wechat_chatrooms`) 中的 `chatroom_version` 和会话表中的 `last_member_sync_version`。
- **效果**：**只有在群成员真正发生变动（版本号变化），或者首次投影该群时**，才会去查询 `wechat_chatroom_members` 表并批量 Upsert 到 CRM 会话成员表中。这直接将之前“每条消息 O(N) 的成员写操作”降级为了“仅在人员变动时触发 O(N)，平时 O(1)”。

### 2. 消息触点增量补偿 (Message-Triggered Incremental Compensation)
- **机制**：即使没有触发全量同步，系统也会提取当前消息的 `sender_wechat_id` 和当前登录账号 `my_wechat_id`。
- **触发**：通过 `_upsert_group_participant_members` 方法，核对这两个核心参与者是否在已知的 `known_member_ids` 集合中；如果不在，则单独为他们进行精确的单条 Upsert。
- **效果**：这是一种非常巧妙的“兜底防错”机制。如果因为某些极端并发情况导致版本号未及时更新，系统依然能保证当前发言的人（和当前号）被安全地投影到成员表中，不会出现“有消息无此人”的参照完整性断裂。

---

## 为什么给 9.5 分？(合理性分析)

### 优点 (加分项)
1. **彻底解决 I/O 放大**：完全消除了 500 人大群在活跃时对数据库造成的写放大灾难。
2. **无侵入的解耦设计**：它没有改变底层的微信 API 同步逻辑（底层依旧由 `contact_sync_service` 负责维护最新版本号和成员），而是巧妙地在 CRM 投影层做了一层“防波堤”。
3. **最终一致性与实时性的完美平衡**：版本对比保证了“最终一致性”，而对 `sender` 的点对点补偿保证了“局部实时性”，在业务侧看来是无缝的。

### 为什么扣掉 0.5 分？(微小的优化空间)
- **并发下的锁竞争隐患**：在极端高并发（例如某大群短时间内爆发 100 条消息，且刚好此时 `chatroom_version` 发生变更）时，这 100 个处理这批消息的 worker 可能会同时发现版本不一致，从而引发“并发全量同步”的雷群效应（Thundering Herd），导致瞬间对同一群组的大量并发 Upsert。
- **优化建议**：如果在未来压测中发现这个问题，可以在触发全量同步前引入 Redis 的分布式锁（或利用 Supabase 的某些 advisory lock 机制），或者将“群成员全量投影”本身也拆分成一个异步延迟去重的单独 Job。

## 总结
这是一个非常成熟、符合 B2B CRM 实际应用场景的解决方案。代码改动精准且优雅，彻底解决了原有的性能痛点，方案十分完善合理。
