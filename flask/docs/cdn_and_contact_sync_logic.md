# 缓存未命中与刷新及群聊/联系人同步逻辑详细说明

本文档详细解释了微信机器人系统中关于 CDN 状态缓存刷新机制，以及获取群聊和联系人的核心同步逻辑。特别是在引入了“基础通讯录层 + CRM投影层”解耦架构后的最新实现机制。

## 1. 缓存未命中与刷新 (refresh_cdn_state) 机制

在处理多媒体消息（如语音、图片、视频、文件等）的下载时，系统需要获取有效的 CDN 参数（`cdn_info`）。为了避免频繁调用微信接口，系统实现了一套缓存与刷新机制。

### 1.1 如何判断缓存是否存在或已过期 (Cache Miss)？

判断逻辑位于 `CdnStateService.get_or_refresh_cdn_state` 方法中。系统会查询数据库表 `cdn_runtime_state` 中对应机器人实例（`guid`）的最新一条记录。只有当以下四个条件**全部满足**时，才被认定为缓存命中（Cache Hit）：

1. **记录存在**：数据库中能查询到对应 `guid` 的记录。
2. **字段完整**：该记录中包含了非空的 `cdn_info` 字段数据。
3. **未过期**：记录中的 `expires_at`（过期时间）字段晚于当前的 UTC 时间。

如果上述任何一个条件不满足，则判定为**缓存未命中**（Cache Miss），随后触发 `refresh_cdn_state` 刷新缓存。

### 1.2 缓存是如何生成的？

当发生缓存未命中时，`refresh_cdn_state` 方法将执行以下步骤生成新缓存：

1. **接口调用**：通过 `guid_client` 调用微信底层的 `/cdn/get_cdn_info` 接口，传入当前机器人的 `guid`、相关的 `username`（或 `room_username`）。
2. **数据提取**：解析接口返回的数据，提取出关键参数，如 `cdn_info`、`device_type`（设备类型）、`client_version`（客户端版本）等。
3. **计算过期时间**：系统将当前时间记为 `fetched_at`，并将过期时间 `expires_at` 设定为**当前时间 + 3 小时**。
4. **持久化落库**：将以上数据组装为一条记录，使用 `upsert`（插入或更新）操作，以 `guid` 为冲突检测键（`on_conflict="guid"`）写入到 `cdn_runtime_state` 数据库表中。

### 1.3 cdn表里永远只有一行数据吗？

**不一定**。
`cdn_runtime_state` 表的唯一约束/主键是 `guid`（机器人实例 ID）。
- 如果系统只运行了**一个**微信机器人实例（即只有一个 `guid`），那么表里**永远只有一行数据**。每次刷新缓存时，都会直接覆盖（Update）这一行。
- 如果系统以多租户模式运行了**多个**不同的微信机器人实例（多个不同的 `guid`），那么表里会有**多行数据**，每个 `guid` 各占一行，互不干扰。

### 1.4 是下载文件失败后会去调用获取 cdn 参数吗？

**不是在失败后，而是在下载前置阶段。**

逻辑位于 `MediaWorker._handle_download_media` 方法中：
1. **下载前置调用**：在构建向云端发起的媒体下载请求（`download_body`）**之前**，系统会首先调用 `get_or_refresh_cdn_state` 确保拿到有效的 CDN 凭证。
2. **失败重试机制**：如果云端下载失败抛出异常，系统并不会在当前的执行上下文中立刻触发刷新 CDN 参数。而是标记任务失败，依赖于外部的 Job 调度系统（`JobService`）在后续进行**任务重试**。
3. 当该下载任务被重新调度执行时，会**再次完整走一遍前置流程**。此时，如果上次缓存的 CDN 参数已超过 3 小时，就会自然触发过期刷新，获取新的参数。

## 2. 获取群聊和联系人的相关同步逻辑

系统的联系人与群聊同步是一套设计精妙的**增量同步架构**，主要由 `ContactSyncService` 负责底层通讯录抓取，最终通过 `CrmWxProjectionService` 映射为业务数据。整个架构遵循“底层微信通讯录与顶层 CRM 业务解耦”的原则。

### 2.1 核心同步流程 (底层通讯录抓取)

#### A. 增量序列号发现与防丢机制
系统在 `wechat_sync_state` 表（原为 `crm_wx_sync_state`）中维护了每个机器人对应的同步进度（`contact_seq` 和 `room_seq` 序列号）。
- 每次同步时，读取上次的序列号。如果是 0 则代表全量同步，非 0 则代表增量同步。
- 携带该序列号调用底层微信接口（如 `init_contact`），接口会返回自该序列号之后发生变更的用户名列表（`usernames`）以及新的序列号。
- **防丢保护**：如果接口未返回有效用户名列表（或本地解析提取失败），系统会触发保护机制——**拒绝推进本地序列号**。只有当成功提取并处理了联系人后，才会将新的序列号保存到数据库，确保数据“零丢失”。
- 系统根据返回的用户名后缀（如包含 `@chatroom`），将其划分为**普通联系人**和**群聊**两类。

#### B. 简要信息批处理
对于获取到的变动用户名列表，系统不会逐一调用详情接口，而是：
1. **分批获取**：将用户名分为 50 个一组的批次，调用 `batch_get_contact_brief_info` 获取基础信息（昵称、头像等）。
2. **基础表落库**：获取到的数据会被分类存入 `wechat_contacts`（联系人）、`wechat_chatrooms`（群组）和 `wechat_chatroom_members`（群成员）这三张基础通讯录表中。

### 2.2 群聊同步的“混合缓存补偿”策略

群聊的同步最为复杂且高频，为了极大降低对微信接口的请求压力并解决性能瓶颈，系统采用了**双版本号（Version Control）比对 + 触点增量补偿**的混合缓存机制：

1. **群资料版本 (`chatroom_info_version`)**：
   - 代表群的静态资料（如群名称、群公告、群主等）版本。
   - 系统将本地 `wechat_chatrooms` 表中存储的版本与接口返回的版本进行比对，若不一致，才调用 `_fetch_room_profile` 获取最新资料。
2. **群成员版本 (`chatroom_version`) 惰性全量同步**：
   - 代表群成员列表的版本。
   - 只有当 `CrmWxProjectionService` 在处理某条具体聊天记录时，发现原始通讯录中的群版本号落后于最新版本，才会去调用接口拉取**全量群成员列表**，从而将 O(N) 的更新操作降维至 O(1)。
3. **消息触点增量补偿 (兜底机制)**：
   - 在处理每一条微信聊天记录时，投影服务会强制核对该消息的“发送者”和“接收者”是否存在于本地群成员表中。
   - 如果发现核心角色缺失（例如刚刚进群发了第一句话的人），即使未触发群版本更新，系统也会立刻单独对该发信人执行单点信息插入，保证“绝对不会出现找不到发信人”的情况。

### 2.3 数据快照持久化 (Snapshot)
无论同步下来的是普通联系人还是复杂的群聊资料，系统都采用了一种兜底的**快照模式**：
- 每次从接口拿到的原始微信 JSON 报文，会被完整无损地存储到对应表的 `raw_json` 字段中（如 `wechat_contacts.raw_json`）。
- 这种设计极大地增强了系统的鲁棒性，即使未来需要新增结构化字段，也无需重新发起网络请求，直接解析历史快照即可。

### 2.4 业务层投影与智能匹配 (Projection & Binding)
原始数据同步到 `wechat_contacts` 和 `wechat_chatrooms` 等基础表后，通信层的数据收集即告完成。
随后，`CrmWxProjectionService` 负责进行高阶的业务映射：
1. **上下文补齐**：查询基础通讯录表，把冷冰冰的 `wxid` 翻译成真实的微信昵称或群名片（`display_name` 优先）。
2. **生成正式会话/消息**：将解析后的数据写入正式的 CRM 表（`crm_wx_conversation` 和 `crm_wx_message`）。
3. **手动绑定优先**：
   - 私聊和群聊均不再做自动候选推荐。
   - 私聊会话由业务人员手动绑定 `customer_id + primary_contact_id`。
   - 群聊会话由业务人员手动绑定 `customer_id`。
